## 3. Bugs found and fixed

Each was reproduced first, fixed, then re-measured. Nothing was changed on
suspicion alone.

### 3.1 `np.array(result, copy=True)` handed back the internal array

All four array-like results in this scope — `TopologyResult`,
`OptimizationResult`, `SensitivityResult`, `ForceIdResult` — implemented
`__array__(self, dtype, copy)` but ignored `copy`. Under the NumPy 2 protocol
that means `np.array(result, copy=True)` returns a *view*, so writing into what
the caller believes is a private copy silently corrupts the result object:

```python
a = np.array(topology_result, copy=True)
a[0, 0] = 12345.0
topology_result.density[0, 0]   # -> 12345.0
```

All four now delegate to `np.array(field, dtype=dtype, copy=copy)`, which
implements the protocol exactly: `copy=True` copies, `copy=False` refuses to
cast, `copy=None` copies only if needed. `np.asarray(result)` still returns a
view, so the cheap read-only path is unchanged.

Confirmed fixed on all four; `np.asarray` still shares memory.

### 3.2 GCV returned an arbitrary regularisation parameter for square systems

This is the worst of the six. With the library's **default** arguments
(`method="tikhonov"`, `alpha="gcv"`), a perfectly conditioned, noise-free 2×2
force identification returned essentially zero force:

```
truth F = [2+1j, -1+0j]
identified = [0.0107+0.0069j, -0.0003+0.0032j]      alpha = 12.5
```

`pinv`, `tsvd` and `tikhonov` with any explicit `alpha` all got it exactly
right, which is what pointed at the parameter selection rather than the solve.

GCV needs residual degrees of freedom. Its denominator is
`m - sum_i s_i^2/(s_i^2 + a^2)`; when the number of measurements `m` does not
exceed the number of unknown forces, numerator and denominator both vanish like
`a^4` as `a -> 0`, the criterion is flat, and the grid search returns whichever
end of the grid happens to score lowest. `_gcv_alpha` now returns 0 for
`m <= min(m, n)` — there is no noise level to estimate from a square system, so
declining to regularise is the honest answer, and `max_condition=` remains as
the explicit override.

Measured deviation from the least-squares solution, before → after:

| transfer matrix | before | after |
|---|---|---|
| 2×2 | 1.13e-4 | **0** (alpha = 0) |
| 3×3 | **2.45e-1** | **0** |
| 2×3 (under-determined) | 7.57e-6 | **0** |
| 3×2 (over-determined) | 3.81e-7 | 3.81e-7 (unchanged) |
| 4×2 (over-determined) | 8.19e-7 | 8.19e-7 (unchanged) |

The over-determined case — the one GCV is actually defined for, and the one the
round-1 report benchmarked — is untouched.

### 3.3 The L-curve was not finding the L-curve corner

`_lcurve_alpha` scores candidates by curvature,
`|rho' eta'' - eta' rho''| / (rho'^2 + eta'^2)^{3/2}`. Wherever the L-curve is
locally flat that is 0/0, which produces a NaN — and `np.argmax` on an array
containing NaN returns the index of the *first NaN*, not the maximum. So the
selected parameter was "wherever the curve first goes flat".

On a 400-line ill-conditioned problem, **398 of 400 lines** contained a NaN, and
on every one of those `argmax` disagreed with `nanargmax`, by up to **9.0
decades** in `alpha`. It also emitted a `RuntimeWarning` on every call.

Flat stretches now score zero curvature instead of NaN. The corrected criterion
behaves the way the textbook says it should — and, importantly, it is now the
best estimator in exactly the regime the L-curve exists for:

| case | noise | pinv | GCV | L-curve |
|---|---|---|---|---|
| well conditioned (cond 2e0) | 0 % | 2.0e-16 | 8.0e-7 | 5.1e-1 |
| well conditioned | 1 % | 4.2e-3 | 4.2e-3 | 4.2e-3 |
| ill conditioned (cond 2e8) | 0 % | 1.3e-8 | 1.3e-8 | 4.6e-1 |
| ill conditioned | 1 % | 7.3e+5 | 4.9e-3 | **3.5e-3** |
| ill conditioned | 5 % | 3.9e+6 | 2.5e-2 | **1.7e-2** |

The selected `alpha` now also rises monotonically with the noise level
(1.3e-3 → 5.1e-3 → 1.2e-2 → 1.5e-2 for 0.1 / 1 / 5 / 10 % noise), which is the
signature of a corner that is actually being located. The over-smoothing on
noise-free data (4.6e-1) is the well known L-curve failure mode, already
documented in the round-1 report; before the fix it was masked by the NaN
accidentally forcing a tiny `alpha`.

### 3.4 `size_optimize(tol=...)` was silently ignored by every method but SLSQP

`tol` was written into the `options` dict for SLSQP / COBYLA / trust-constr and
then unconditionally removed again by `opts.pop("tol", None)` one line later,
and it was never passed to `minimize` itself. Reproduced on five methods —
`tol=1.0` and `tol=1e-12` produced byte-identical results and identical
evaluation counts for COBYLA, trust-constr, Nelder-Mead, Powell and BFGS.

`tol` now goes to `scipy.optimize.minimize(tol=...)`, which translates it into
each method's native tolerance. After the fix:

| method | `tol=1` | `tol=1e-12` |
|---|---|---|
| COBYLA | 7.6e-2 (8 fev) | 4.3e-26 (106 fev) |
| trust-constr | 18.0 (5 fev) | 4.5e-12 (49 fev) |
| Nelder-Mead | 18.0 (4 fev) | 5.0e-26 (195 fev) |
| Powell | 0.0 (27 fev) | 0.0 (140 fev) |
| BFGS | 18.0 (5 fev) | 4.5e-12 (137 fev) |

SLSQP is unaffected: SciPy's own `options.setdefault("ftol", tol)` sets exactly
what the removed line was setting.

### 3.5 `size_optimize(method="trust-constr")` crashed

```
ValueError: operands could not be broadcast together with shapes (0,) (2,)
```

`trust-constr` reports the objective gradient as `res.grad` and reuses
`res.jac` for the list of *constraint* Jacobians — which is `[]` for an
unconstrained problem. The result packing assumed `res.jac` was always the
objective gradient. A new `_objective_gradient` helper picks `grad` first, falls
back to `jac`, and validates the length against the number of design variables
before scaling, returning `None` rather than crashing when neither fits.

### 3.6 The density filter did not enforce the volume constraint it was given

The OC bisection compared `sum(x_new)` — the *design* variables — against the
target. Under a sensitivity filter those are the physical densities and it is
correct, but under `filter="density"` the physical field is `H x / Hs`, and the
filter is not volume preserving near the mesh boundary. The published 88-line
reference bisects on `sum(xPhys)` for exactly this reason. Reproduced as a
volume error growing with the filter radius:

| `rmin` | achieved volume fraction (target 0.400000) | after |
|---|---|---|
| 1.5 | 0.400103 (+0.026 %) | 0.400000 |
| 2.0 | 0.400581 (+0.145 %) | 0.400000 |
| 3.0 | 0.399229 (−0.193 %) | 0.400000 |
| 4.0 | 0.396562 (−0.859 %) | 0.400000 |
| 6.0 | 0.390508 (**−2.373 %**) | 0.400000 |

`_oc_update` now takes an optional `physical` transform and evaluates it inside
the bisection. The constraint is met exactly at every radius. Using the material
it was actually allotted also makes the designs better — compliance at
`rmin=6` drops from 263.60 to 250.62.

The sensitivity filter (the default, and the one `tests/test_topology.py`
exercises) passes `physical=None` and is bit-for-bit unchanged: the 60×20 MBB
benchmark still gives compliance **203.31** at volume fraction exactly 0.500000
in 94 iterations.

## 5. Notes for other agents

- **`femtools.pretest` and `femtools.fea` have the same `__array__` bug I fixed
  in §3.1.** `pretest/target_modes.py:166` and `pretest/_result.py:30` both use
  `astype(dtype, copy=False)` and ignore the `copy` argument;
  `fea/static.py:34` does not accept `copy` at all, which makes NumPy fall back
  to a slower path. The one-line fix is `np.array(field, dtype=dtype,
  copy=copy)`. Owners: R3-O3 and R3-O1.
- **R3-F2:** the `ModalResult.frequencies` → `freq_hz` rename is the kind of
  change that breaks consumers silently. This package survived only because it
  probes both names. Worth a grep for `.frequencies` across the tree.
- **R3-G1:** `ruff check .` over the whole repository reports exactly one error,
  `I001 Import block is un-sorted` in `tests/test_public_api.py:3`, and it is
  auto-fixable (`ruff check --fix tests/test_public_api.py`). My four packages
  are clean. Also, if you want a regression test for any of the six fixes, the
  cheapest high-value ones are (a) `np.array(result, copy=True)` not aliasing,
  which is three lines and catches a whole class of protocol bugs, and (b)
  `topology_simp(filter="density", rmin=6)` hitting its volume fraction, which
  is the one that was quantitatively wrong by 2.4 %. A GCV test needs only a
  2×2 matrix and an exact expected answer.
- **Still open from round 2, still true:** EFDD damping carries 10–15 % scatter
  on a finite record; a two-parameter beam updated from noisy frequencies alone
  is genuinely ill-conditioned; and MPE observability means you should derive
  the expected mode list from modal participation, not from the frequency list.
- `docs/algorithms/optimization.md` §1 still documents a model-first
  `size_optimize(model, design_vars, objective, ...)` while the implementation
  is callable-first. Unchanged from round 2 — no caller wants the documented
  form, so I left the signature alone rather than churn it.
