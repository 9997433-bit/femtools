## The new API

```python
map_nearest_nodes(xyz_test, xyz_fe, *, tol=None, unique=False) -> NearestNodeMap
mac_contribution(phi_a, phi_b, index_a=None, index_b=None, *, weights=None, normalize=False)
```

### `map_nearest_nodes` — which node is this accelerometer on?

Returns `NearestNodeMap`, a two-field `NamedTuple`, so the documented `(fe_ids, distances)` contract
is literally what it is — `fe_ids, dist = map_nearest_nodes(...)` unpacks, `isinstance(..., tuple)`
holds, `result[0]` works — with the quality figures reachable as attributes: `matched`, `unmatched`,
`n_matched`, `is_one_to_one`, `max_distance`, `rms_distance`, `table()`.

* **Inputs.** Both sides take an `(n, 3)` array, a planar `(n, 2)` one (padded to `z = 0`), a
  `{node: xyz}` mapping, an `(ids, xyz)` pair, or an `FEModel` / anything carrying nodal
  coordinates. The result is one row per test point, in test order. A bare FE array carries no ids,
  so the returned "ids" are then its row positions — which is exactly what you want for slicing the
  array back.
* **`tol`.** A test point whose nearest node is further away comes back as `-1` instead of being
  welded to a node it does not belong to; its **true distance is kept**, so the threshold can be
  judged from the result. This is the whole point of returning distances: a channel digitized 30 cm
  off is a bookkeeping error, and correlating it silently blames the model for it.
* **`unique=True`.** Forces a bijection. The plain nearest-neighbour map is returned *unchanged*
  when it is already injective — it then attains the lower bound (every row holds its own minimum),
  so it is the optimal matching and there is nothing to solve. Only on a collision is the minimum
  total distance solved with the same rectangular assignment `pair_modes(method="hungarian")` uses
  (`correlation/_assignment.py`, untouched). Surplus test points (more channels than nodes) come
  back unmatched.
* **Tie breaking.** A point equidistant from two nodes — routine on a symmetric mesh, e.g. a sensor
  at the middle of an edge — resolves to the lower node position, on **both** search paths, so the
  answer does not depend on the size of the model or on whether SciPy is present.
* **Exactness.** Distances are computed from the straight coordinate difference, never from the
  `|q|² + |r|² − 2 q·r` expansion. The expansion is faster (one BLAS `gemm`) but loses half the
  significant digits near zero: on the identical-cloud case at 1e6 it returns ~1e-10 instead of 0.
  The KD-tree path recomputes the distance to the node it picked for the same reason, so the two
  paths return **bit-identical** distances.
* **Cost.** Exact chunked search up to ~2M point pairs, `scipy.spatial.cKDTree` above that (250
  sensors × 64 000 nodes: 52 ms vs 178 ms brute, same answer bit for bit). `unique=` never builds
  the full cost matrix: only nodes that an optimal assignment can use are kept — the union of each
  row's `n` nearest, which is optimality-preserving because at most `n − 1` of a row's `n` nearest
  can be taken by other rows — reducing 64 000 nodes to 892 candidate columns in the scale probe.
  Past `_ASSIGN_ENTRY_LIMIT` the call raises with what to do instead rather than allocating.

Composes with the alignment step, which is the realistic pipeline (digitized geometry is in the
tracker frame):

```python
fit = align_geometry((known_ids, ref_points), model)   # test frame -> FE frame
ids, dist = map_nearest_nodes(fit.apply(test_xyz), model, tol=0.01)
lookup = dict(zip(channel_ids, ids))
fe_map = DOFMap([lookup[n] for n in test_map.nodes], test_map.components, test_map.scale)
```

### `mac_contribution` — where a MAC value comes from

A MAC of 0.62 says the shapes disagree but not where. The MAC is a squared inner product and an
inner product is a sum over DOFs, so the value splits **exactly** — no modelling choice, no
re-normalization:

```
c[q] = Re( conj(a[q]) (W b)[q] * conj(a^H W b) ) / ((a^H W a) (b^H W b))
sum_q c[q] = |a^H W b|^2 / ((a^H W a)(b^H W b)) = MAC(a, b)
```

For real modes that is just `a[q] b[q] (a^T b) / (‖a‖² ‖b‖²)`. Reading it: a large positive entry is
a DOF that agrees and carries amplitude; a **negative** entry is a DOF moving against the overall
correlation — the local sign flip or the reversed sensor pulling the MAC down; a near-zero entry is
a DOF the MAC cannot see either way. `sum_q |c[q]| ≥ MAC`, and the gap between the two is exactly
the cancellation the MAC suffers.

* Same inputs as `mac_value` (1-D vectors, `(n_dof, 1)` columns, a `ModalResult`, `weights=` scalar
  / 1-D diagonal / dense / sparse).
* `index_a` / `index_b` pick the pair out of two full mode sets, i.e. they name the entry
  `mac_matrix(phi_a, phi_b)[index_a, index_b]` that is being explained. Matched sets of equal size
  give a `(n_dof, n_pair)` array whose column sums are `mac_pairs`.
* `normalize=True` divides by the MAC, so the contributions read as the fraction each DOF supplies
  and sum to 1 (all-zero, not NaN, for a null pair).
* It is *not* a COMAC: COMAC aggregates across several pairs into a `[0, 1]` ratio per DOF;
  this is a signed additive split of one MAC value. Both are in the package and the docstrings
  cross-reference each other.

### End to end, on a solved model

A 13-node portal frame (BEAM2, clamped at both feet), 11 channels digitized in a tracker frame
rotated 37°, translated, shuffled, with 0.8 mm noise:

* `align_geometry` on **three** known reference targets recovers the rotation to 5e-3, then
  `map_nearest_nodes` assigns all 11 channels to the right FE nodes, 1-1, max distance 2.8 mm.
* A channel displaced by 30 cm is rejected by `tol=0.01` (`-1`, distance 0.2999) instead of stealing
  a node; two channels digitized onto the same node collide under the plain map and are separated by
  `unique=True`.
* Relabelled onto FE node ids, `align_modes` + `mac_matrix` give a MAC diagonal of 0.9999.
* Reversing one accelerometer drops the MAC of some modes (0.9515, 0.9725) and leaves others
  untouched (0.9999 — that node barely moves in them). `mac_contribution` returns the reversed
  channel as the single negative DOF **for every mode**, and its contributions sum to the MAC value
  to 1e-14.

## Three small things fixed along the way

1. **`align_geometry` now accepts a model.** `map_nearest_nodes(xyz, model)` worked while
   `align_geometry(xyz, model)` — the step immediately before it in the same workflow — died with a
   raw `TypeError: float() argument must be ... not 'FEModel'`, even though its own docstring points
   at `node_coordinates` for exactly that input. Model-like sources now fall through to the shared
   coordinate reader (keeping their node ids, which is what lets the fit match the two clouds by
   number), and an unusable object gets a sentence saying what the argument takes. Purely additive:
   every input that worked before is handled by the same branches as before, and the inputs that now
   work used to raise.
2. **`node_coordinates` docstring corrected.** It claimed "a `ModalResult` reaches its model through
   `assembly`". It cannot: `AssemblyResult` carries `K`, `M`, `C`, the DOF map and `node_ids`, but no
   geometry, so `node_coordinates(modal)` has always returned `None` (and `CandidateSet.coords` is
   `None` unless `coords=` is passed). The docstring now says so and tells the caller to pass the
   model. Documentation only — no behaviour changed, and fixing it for real means adding coordinates
   to the kernel result objects, which is outside my paths. The same paragraph now also states the
   ordering rule that was easy to misread: without `per_dof` the rows are one per node in **ascending
   node id**, not in the map's order.
3. **The point-cloud reader is now shared.** `_coordinate_table` / `_xyz_array` / `_node_xyz` moved
   verbatim from `pretest/candidates.py` to `correlation/_linalg.py` (the module whose docstring
   already says "shared by the correlation and pretest packages") as `coordinate_table` /
   `xyz_array` / `node_xyz`. `correlation.dofmap` cannot import `pretest.candidates` at module level
   — `candidates` imports `dofmap` — so the alternative was a deferred import inside the function.
   Private, no public name changed.
