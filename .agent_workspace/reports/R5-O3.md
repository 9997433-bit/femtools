# R5-O3 — bug hunt in `correlation/**` and `pretest/**`

Exclusive paths written: `src/femtools/correlation/**`, `src/femtools/pretest/**`, this report.
Nothing outside them was touched. No git operations performed.

## Summary

Round 5 was a defect hunt, not a feature round: no new API, no signature changes, no behaviour
change on any input that already worked. Eight modules of the two packages were re-read line by
line and then attacked with twelve throwaway probe scripts (~330 assertions) built around
brute-force references, independent replays, exhaustive-search optima, SciPy cross-checks and one
end-to-end run on a solved FE model.

**The core numerics are sound.** MAC (real, complex, weighted, sparse-weighted), COMAC, ECOMAC,
MSF, cross-orthogonality, FRAC/CSAC/CSF/FDAC, EFI, effective mass, SEREP, static and dynamic
Guyan, mass loading and the Procrustes fit were all checked against independent references and
matched to 1e-15..1e-10. Nothing in those kernels was changed.

**Seven defects were reproduced and fixed**, all in the layer that interprets user input or
translates an option into a decision. Two of them silently returned wrong numbers, four silently
ignored or misread an argument, and one turned a well-posed problem into a worse answer than the
cheaper method it is supposed to beat.

`pytest`: **99 passed, 3 skipped** (the suite grew from 68 during the round — R5-G1's new tests
pass unchanged). `ruff check`, `ruff format --check` and `mypy` clean on all 18 files.
`tests/test_mac.py`, `tests/test_efi.py`, `tests/test_round4_fmac.py`, `tests/test_pairing.py` and
`tests/test_public_api.py` pass untouched, as do `examples/pretest_efi.py`, `examples/mac_demo.py`
and `examples/guyan_serep.py`.

## The seven bugs

### 1. A lumped mass silently corrupted the dynamic expansion — `expansion.py`, `dofmap.py`

`expand_guyan(..., mass=m, freq_hz=f)` builds the slave partitions with
`restrict(mass, slave)` and `restrict(mass, slave, master)`. `restrict` reads a 1-D array as a
lumped diagonal and returns the sub-*vector* `m[rows]` — **ignoring the column selector**. The
dynamic expansion then computed `K_ss - w² m_slave` (a vector broadcast against a matrix, so every
row of the stiffness got the same subtraction) and `m_sm @ psi_m` as a dot product.

Everywhere else in the package — `cross_orthogonality`, `effective_mass`,
`nodal_kinetic_energy`, `weighted` — a 1-D array *is* a valid lumped mass, so this is an input a
user has every reason to pass. When the slave and master counts differed it raised a shape error
from deep inside NumPy; **when they happened to match it returned finite, plausible, wrong mode
shapes**. On a 6-DOF chain with 3 masters the expanded shapes were off by 0.34 in absolute
amplitude, with no warning of any kind.

Fixed on both sides. `expand_guyan` now materializes a 1-D mass into a real diagonal operator
(sparse or dense to match the stiffness) and validates its size, and `restrict` refuses the
genuinely ill-posed 1-D-plus-column-selector call instead of answering it with the sub-vector.
`expand_guyan` is the only caller that passed a column selector, so no other behaviour moved.

Verified: all five sparse/dense/lumped combinations of `(K, M)` now agree to 1e-16; the dynamic
expansion stays exact on true eigenpairs (7.8e-16 on the chain, 1.2e-10 on the L-frame's free
partition); static Guyan is bit-identical to before; both wrong-size mass forms are now reported
with the size that was wrong.

### 2. `sensor_mass_limit` misread a boolean sensor mask — `mass_loading.py`

`mass_loading(phi, f, m, dofs=mask)` accepts a boolean mask; its companion
`sensor_mass_limit(phi, shift, dofs=mask)` cast the same mask straight to integers, so
`[F, F, T, F, T, F]` selected rows `0,0,1,0,1,0` — six limits for the wrong DOFs instead of two
limits for the right ones. Both functions now go through the shared `row_index` helper, which
expands a mask and validates its length. That also closes the same hole in `mass_loading`, where a
wrong-length mask silently selected from a prefix of the rows.

While there: `sensor_mass_limit` now validates `generalized_mass` (wrong length used to surface as
a NumPy broadcast error naming shapes the caller never wrote; non-positive values were accepted).

Verified: mask and positions agree; each per-DOF limit hits the 1 % budget exactly when applied
alone, and `n_sensors=` keeps a shared budget inside it.

### 3. Documented coordinate inputs were rejected, and one degraded to `None` — `candidates.py`

`node_coordinates` documents "a ``{node: xyz}`` mapping, an ``(n_node, 3)`` array"; only the
mapping worked. A bare array raised *"no nodal coordinates found on the given source"*, and the
`(ids, xyz)` pair that `align_geometry` takes was not recognized either.

The consequence was worse one level up: `candidate_dofs(coords=xyz_array)` resolves coordinates
with `missing="none"`, so the array was **silently discarded and `CandidateSet.coords` came back
`None`** — which then disables `min_separation` in `select_exciters` without saying so.

`_coordinate_table` now understands the array and the `(ids, xyz)` pair (padding a 2-D planar
cloud to 3-D, as the alignment side does). A bare array carries no node ids, so its rows are read
positionally against `np.unique(dof_map.nodes)` — the convention `rigid_body_modes` already uses —
and a row count that does not match is reported rather than dropped.

That exposed a second, related defect: `candidate_dofs` resolved the coordinates against the
*retained* candidate map, so a positional array stopped matching the moment `active_only` dropped
a constrained node — exactly the L-frame case, where the map covers 20 nodes and the array 21.
Coordinates are now resolved against the whole DOF map and sliced afterwards.

Verified on the L-frame: the model, an `(ids, xyz)` pair and a bare array now all give the same
`(60, 3)` candidate coordinates.

### 4. `mac_limit` was silently ignored for two of the three criteria — `sensor.py`

`eliminate_by_mac`'s `mac_limit` is documented without qualification, but the check read
`criterion == "max" and scores[best] > mac_limit`. With `criterion="sum"` or `"mean"` the score is
the *total* off-diagonal MAC, not the largest, so the limit was simply never consulted: a run with
`mac_limit=0.05` returned a set whose worst off-diagonal MAC was 0.0601.

The limit is a property of the set that would be left, so `_removal_scores` now returns the
resulting worst off-diagonal alongside the criterion score (free — it already computes the whole
MAC matrix of every candidate) and a removal that would breach the limit is *skipped* rather than
ending the loop. Skipping matters for `sum`/`mean`: the removal that minimizes the total is not
the one that minimizes the maximum, so breaking would have stopped while a different, admissible
removal was still available. For `criterion="max"` the two quantities coincide and the behaviour
is unchanged.

Verified: over 150 random candidate sets × 3 criteria, the limit is never breached *and* the stop
is tight — no single further removal would have stayed inside it. Without a limit all three
criteria still reach the requested count, and greedy `"max"` still matches an independent replay
of the elimination.

### 5. A single NaN aborted all mode pairing — `pairing.py`

`pair_modes(..., mac=user_matrix)` with one non-finite entry: greedy hit it on its first `argmax`,
failed the `np.isfinite` guard meant for its own `-inf` sentinel, and **returned zero pairs** —
silently, for a matrix whose other modes correlate at 0.99. The Hungarian path raised
*"cost matrix must be finite"* instead. Non-finite entries are now masked out of the admissible
set, so both strategies treat them as "these two must not pair" and report the affected modes as
unpaired, which is the only meaningful reading.

### 6. The "globally optimal" pairing was beaten by greedy — `pairing.py`

Reproduced while fixing 5, but independent of it and reachable through the plain documented API.
Two separate flaws in `_hungarian`:

*The threshold was applied to the answer instead of to the problem.* The solver maximized the
total MAC over **all** cells and `mac_threshold` filtered the result afterwards, so the assignment
optimized an objective that included pairs it was never allowed to report. On

```
MAC = [[0.90, 0.80],     mac_threshold = 0.6
       [0.50, 0.00]]
```

greedy returns the correct `(0,0)` at 0.90; `"hungarian"` returned `(0,1)` at 0.80, because
`(0,1)+(1,0) = 1.30` beats `(0,0)+(1,1) = 0.90` before the threshold is applied and only `(0,1)`
survives it. Across 2000 random thresholded problems, the method documented as *globally optimal*
lost to greedy in **249**.

*The forbidden-pair penalty displaced good pairs.* Cells excluded by `freq_tol` (or now by a
non-finite MAC) were costed at `max(MAC) + 1`. The solver must assign every row, so rather than
pay that penalty once it moved an unrelated well-correlated pair onto a worthless cell — and that
pair was then dropped along with the forbidden ones.

Both are fixed by modelling "unpaired" honestly: the threshold and the frequency window define one
admissible set, an inadmissible cell costs **0** — exactly what leaving a mode unpaired is worth —
and admissible cells cost `-MAC ≤ 0`. The optimum of that problem is the maximum-weight matching
over the admissible cells, with no penalty constant to tune.

Verified against an exhaustive matching search over 400 random rectangular problems with random
forbidden cells and random thresholds: exact agreement. Hungarian is now never worse than greedy
(0 of 400, and 0 of 2000 thresholded), and on matrices with nothing forbidden and the default
threshold the cost matrix is identical to before, so the common path is untouched (300 cases
re-checked against the exhaustive optimum).

### 7. `select_exciters` returned an empty selection when everything was excluded — `exciter.py`

`exclude=` covering every candidate produced a result with zero drive points, `coverage` all zero
and no error — while the caller had asked for three. The documented early stop is the
`min_separation` one ("the selection stops early if no candidate is far enough away"), which is a
geometric fact about the structure; an `exclude` list that leaves nothing is a configuration
mistake and now raises. The `min_separation` early stop is unchanged and still verified.

## Not bugs (checked, deliberately left alone)

* **`select_exciters` is a local optimum.** Against exhaustive search over 2-of-8, the refined
  selection is suboptimal in 9 of 200 cases. This is the documented limit of a greedy-plus-exchange
  search on a max-min cover, already recorded in R4-O3, and the gaps are small.
* **A `ModalResult` yields `coords=None`.** It reaches an `AssemblyResult`, which carries
  `node_ids` but no geometry, so there is nothing to find; `candidate_dofs(coords=model)` is the
  supported route and works. Now covered by a probe so it cannot be mistaken for defect 3.
* **`select_target_modes` normalizes a raw effective-mass array by its own column sums** rather
  than by the true rigid-body mass. It cannot know the latter from an array; passing an
  `EffectiveMassResult` gives the true fraction.
* **The dynamic expansion is not exact against the *unconstrained* `K`, `M`** of a model with
  SPCs — those rows carry the support reactions, so `(K - w²M)ψ = 0` does not hold there. On the
  free partition it is exact to 1.2e-10.

**End-to-end.** L-frame of 20 BEAM2 elements (10 along x, 10 along y), clamped at node 1, six
target modes at 5.59–86.34 Hz. Target selection → 60 candidate DOFs → 10 EFI sensors
(`21X 21Z 16X 11Z 7Z 21Y 20Y 6Z 12Z 15X`) → 2 drive points ≥ 0.3 m apart (`17X 21Z`) → sensor mass
budget → a test data set digitized in a frame rotated 9° and shifted (0.4, −0.15, 0.8) → alignment
→ expansion → correlation. All 22 checks pass: the Procrustes fit recovers the rotation to
1.6e-16, SEREP reproduces the FE modes at MAC 1.000000, the dynamic expansion is exact to 1.2e-10
on the free partition and beats static Guyan (1.000000 vs 0.983740), a lumped mass now matches its
dense diagonal to 5.6e-13, full-space cross-orthogonality has diagonal 1.000000 and zero
off-diagonal, and the FMAC recovers the injected 4 % frequency bias to five digits under both
pairing strategies. A target mode deleted from the test set is reported unpaired by both, instead
of being force-matched to its neighbour.

## Notes for other agents

* **No API changed.** Every fix is either a previously-broken input now working, a silently-wrong
  answer now correct, or a silently-ignored mistake now raised. Nothing that worked before behaves
  differently, which the unchanged test suite and the three examples confirm.
* **R5-G1 / tests.** Worth locking in, all currently uncovered: a lumped mass in `expand_guyan`
  matching its dense diagonal; `sensor_mass_limit` with a boolean mask; `mac_limit` with
  `criterion="sum"`; `pair_modes(mac=...)` containing a NaN; `"hungarian"` never scoring below
  `"greedy"` for the same `mac_threshold`; `candidate_dofs(coords=array)` returning coordinates.
  The `MAC = [[0.90, 0.80], [0.50, 0.00]]`, `mac_threshold=0.6` matrix of defect 6 is a two-line
  regression test.
* **R5-F4 / CLI + viz.** `CandidateSet.coords` is now populated for the array and `(ids, xyz)`
  coordinate forms, so a `femtools pretest` command can rely on `min_separation` without first
  having to check for `None`.
* **`restrict` is stricter.** `restrict(v_1d, rows)` is unchanged and still returns the sub-vector
  of a lumped mass; only `restrict(v_1d, rows, cols)` — which used to ignore `cols` — now raises.
  No caller outside `expansion.py` passed a column selector.
