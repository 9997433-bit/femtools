## Bugs found and fixed

### 1. A boolean mask silently selected the wrong DOFs

`DOFMap.take`, `DOFMap.__getitem__`, `CandidateSet.take` and `restrict` all normalized their index
argument with `np.asarray(index, dtype=np.intp)`. That casts a boolean mask to `0`/`1` *positions*
instead of expanding it, so a mask selected the first one or two rows rather than the flagged ones — with
no error:

```python
d = DOFMap.from_keys(["1X", "1Y"])
d[np.array([False, True])].labels     # -> ['1X', '1Y']   expected ['1Y']

restrict(np.arange(16.).reshape(4, 4), np.array([False, True, False, True]))
# -> the 4x4 [[0,1,0,1],[4,5,4,5],...]   expected the 2x2 [[5,7],[13,15]]
```

The consequence is worst in `restrict`, which is exactly how a test-DOF mass matrix is built for a
cross-orthogonality check: a mask there returns a wrong-sized matrix of duplicated rows and the POC
silently reports nonsense. Longer masks usually tripped the `DOFMap` duplicate check instead and raised
a misleading `duplicate DOF (1, 1) at positions 0 and 1`.

Boolean masks were already the established convention elsewhere in the two packages —
`mass_loading(dofs=...)` and `candidate_dofs(mode_index=...)` both expand them correctly — so this was an
inconsistency, not an unsupported input.

**Fix.** New shared helper `_linalg.row_index(index, size=None)`: a boolean array goes through
`np.flatnonzero`, anything else is integer positions (negatives still work). Wrong-length masks now raise
instead of silently truncating. Used by all four call sites.

### 2. Documented component labels were parsed character by character

`candidate_dofs` documents `components` as accepting labels `"z"`, `"-Z"`, and `DOFMap.select` /
`from_nodes` take the same argument. A bare string was iterated, so only *single-character* labels
worked; the multi-character forms the docstring advertises raised:

```python
d.select(components="Z")     # worked (one character)
d.select(components="RZ")    # ValueError: unknown DOF component 'R'
d.select(components="-Z")    # ValueError: unknown DOF component '-'
d.select(components="TX")    # ValueError: unknown DOF component 'T'
```

So `translational_dofs(modal, components="z")` worked by accident while `components="-Z"` — the reversed
accelerometer spelled out in the same docstring — failed. The same trap applied to DOF *keys*:
`indices("1Z")` reported `DOF '1' is not in this map` and `from_keys("1Z")` raised
`cannot parse DOF label '1': no component`.

**Fix.** `_as_item_list` wraps a bare string as one item, applied in `parse_components`, `DOFMap.__init__`,
`from_keys`, `from_nodes`, `select` and `indices`. A single label or key is now equivalent to the
one-element list, which is what the docstrings promise. `DOFMap.from_mapping` keeps rejecting bare
strings outright — a whole DOF map built from one string is a mistake, not a shorthand.

### 3. `TargetModeSelection.achieved_fraction` ignored `include`

`select_target_modes` computed `achieved` from the effective-mass criterion and only *then* applied
`include`, so the reported figure described a mode set that was not the one returned:

```python
em = [[0.5], [0.3], [0.15], [0.04], [0.01]]
sel = select_target_modes(f, em, mass_fraction=0.9, include=[4])
sel.indices            # [0, 1, 2, 4]
sel.achieved_fraction  # [0.95]   the real total over those four modes is 0.96
```

The `n_modes` cap recomputed it, so the inconsistency was specific to `include`.

**Fix.** `achieved` is now computed once, from the final `idx`, after every filter. The direction columns
are also resolved once instead of three times, which removes two duplicate `_direction_columns` calls.

## What was checked and found correct

| Area | How |
|---|---|
| MAC / weighted MAC / COMAC / eCOMAC / MSF / POC | element-wise brute force against the textbook definitions, real and complex, incl. null-mode and rectangular cases |
| Cross-orthogonality | mass-normalized eigenbasis reproduces the identity to 4.4e-16 on a real model |
| Pure-NumPy Hungarian (`_assignment._jv`) | 500 random rectangular matrices vs `scipy.optimize.linear_sum_assignment`, incl. heavily tied integer costs — identical optimal cost, correct shape, unique rows/cols, sorted row output |
| Pairing | permutation recovery under sign flips for greedy/hungarian/auto; rectangular both ways; `freq_tol`, `mac_threshold`, unpaired bookkeeping; greedy-suboptimal case where hungarian must win |
| `DOFMap.common` | 50 random map pairs vs a dict-lookup reference, incl. empty maps and negative node ids |
| `from_mapping` | all six documented input forms produce the identical map |
| EFI | `ED` vs the explicit projector diagonal; the full sequential elimination vs a brute-force loop; ids, `keep`, `mass`, `efi-dpr`, batching, rank-deficient partitions |
| `eliminate_by_mac` | greedy elimination vs a brute-force recompute-every-candidate loop; rank-one downdate is exact for complex modes too |
| Mass loading | **exact** against a full generalized eigensolve `eigh(K, M + dM)` when the complete modal basis is supplied, with and without `generalized_mass`; first-order branch agrees to 1e-6 for a small mass |
| Rigid-body modes | brute force per node; `R^T M R` about the CG of a lumped point cloud gives the right total mass, zero static moment and the right `Ixx` |
| Effective mass | sums to `diag(R^T M R)` over a complete basis |
| FRF metrics (FRAC/CSAC/CSF/FDAC) | self-correlation, scale invariance where expected, brute-force references, FDAC symmetry and unit diagonal |
| `select_target_modes` | 400 randomized trials: the returned set always reaches `mass_fraction` per direction when reachable, stays inside the band, and `rejected` complements `indices` |

**End-to-end on a real model.** 20-element cantilever (`Iz = 4 Iy`), solved with `solve_modes`, whole
loop driven by nothing but the `ModalResult` and the `FEModel`:

Feeding a synthetic measured set back in (2 % noise, one accelerometer mounted upside down, 1.5 %
frequency scatter) pairs 0→0, 1→2, 2→4 at MAC ≥ 0.996 and gives POC diagonals ≥ 0.998 — the pairing
correctly skips the strong-axis modes the Z-only channels cannot see. Every DOF-map source
(`ModalResult`, `AssemblyResult`, kernel `DofMap`, `FEModel`) resolves to the same map, and
`index_of((node, comp))` was checked against `modal.dof_map.index(node, comp - 1)` for every DOF.

Bit-identical to round 2 after the fixes: the same EFI selections and `ED` values, the same MAC
elimination set, `examples/pretest_efi.py` (max off-diagonal MAC 0.0502 < 0.15) and `examples/mac_demo.py`
both PASS, `benchmarks/bench_mac.py` still 50 000 DOF x 16 modes in 1.4 ms.

## Compatibility

All three fixes turn a wrong answer or a spurious error into the documented behaviour; no working call
changes its result.

The one behavioural narrowing worth stating: `DOFMap(nodes, "XYZ")` used to expand to three components
and now means a single (invalid) label `"XYZ"`. Nothing in the repository relied on that — I grepped every
caller of `components=`, `from_nodes`, `select`, `from_keys`, `indices`, `take` and `restrict` outside my
two packages, and the only consumer is `cli.py`, which calls `translational_dofs(modal)` with the default
tuple. Passing an explicit iterable, as every existing caller does, is unaffected.

`ruff check`, `ruff format --check` and `mypy` clean on all 15 files of the two packages.

## Notes for other agents

* **Boolean masks now work everywhere in these two packages.** `d[d.components == 3]`,
  `cand.take(mask)`, `restrict(M, free_mask)` all do the obvious thing, and a wrong-length mask raises
  rather than quietly returning the wrong rows. If you kept a `np.flatnonzero(...)` workaround at a call
  site, it is no longer needed (it still works).
* **F4 / CLI.** The suggestion from R2 still stands and is unaffected by these fixes: `femtools pretest`
  ranks all DOFs including rotations and SPC'd rows. `translational_dofs(modal)` →
  `effective_independence(cand.phi, n, candidate_dofs=cand.dofs)` → `cand.take(ranked.index).labels`
  gives a real pretest with labelled output.
* Still deliberately absent: a TAM reduction (Guyan/IRS/SEREP) for a reduced test mass matrix — that
  belongs in `fea`/`dynamics`. `restrict(M, sensor_rows)` remains the pragmatic stand-in, and it is now
  safe to hand it a boolean mask.
