## Bug 1 — `rbpe/rbfit.py`, `mount_stiffness_matrix`: three of the four documented input forms were dead code

The dispatch tested `np.asarray(mounts, dtype=object).dtype != object`, which is **always
false**: forcing `dtype=object` guarantees the result is an object array, so the comparison
can never distinguish a numeric argument from a ragged mount list. Every numeric spelling
therefore fell through to the physical-mount loop and crashed there:

| documented input | before | after |
|---|---|---|
| 3-vector `[100, 200, 300]` | `TypeError: 'float' object is not iterable` | `diag(100, 200, 300, 0, 0, 0)` |
| 6-vector `[1..6]` | `TypeError: 'float' object is not iterable` | `diag(1..6)` |
| `6x6` matrix | `ValueError: cannot interpret mount array([1., 0., 0., 0., 0., 0.])` | symmetrised as-is |
| list of `(pos, dir, k)` | worked | worked |

The fix drops the dtype trick and asks the question the code actually meant: *can this be
coerced to a float array at all?* A physical mount list is ragged (3-vector, 3-vector,
scalar) or holds dicts, so `np.asarray(..., dtype=float)` raises on it, and anything that
survives the coercion is one of the numeric spellings — dispatched by shape, with an explicit
error for a numeric shape that is none of them. All four forms now produce the documented
matrix, and `rigid_body_properties(mount_k=...)` returns the same 12.5 kg body mass whether
the suspension is handed to it as a spring list, a `6x6`, or a 6-vector diagonal.

## Bug 2 — `rbpe/rbfit.py`, `rigid_body_properties`: frequency axis pickup raised on any real FRF object

The frequency axis was resolved with `getattr(frf, "freq_hz", None) or getattr(frf,
"frequencies", None)`. `or` needs the truth value of its left operand, and the truth value of
a multi-element NumPy array is a `ValueError`. The fallback path therefore worked only for a
frequency axis of length 0 or 1 — i.e. never in practice. Replaced with an explicit loop over
the candidate attribute names, taking the first that is not `None`. An FRF object carrying
its own axis now yields the same 12.5 kg as passing `freq_hz=` by hand.

## Bug 3 — `mpe/common.py`, `lsfd`: participation factors came back conjugated, and unscaled

`lsfd` factorises each residue matrix `A_r = phi_r L_r^T` with an SVD and returns the pair.
Two things were wrong with the factorisation:

* the participation row was taken as `conj(Vh[0, :])`. The leading SVD term of `A_r` is
  `(s_0 u_0) Vh[0, :]`, so the participation row *is* `Vh[0, :]`; conjugating it returns the
  complex conjugate of the participation factors;
* the mode shape was then rescaled to a unit driving component, but that scale factor was not
  moved into the participation, so the pair stopped being a factorisation of anything.

Measured on a synthetic 2-mode MIMO case with known truth:

| quantity | before | after |
|---|---|---|
| `MAC(participation, L_true)` mode 1 / 2 | 0.653 / 0.751 | **1.000 / 1.000** |
| `max abs(outer(shape, part) - residue) / max abs(residue)` | not a factorisation | **7.7e-16 / 7.8e-16** |
| same, SIMO | — | 7.8e-16 / 8.1e-16 |

The FRF fit error itself (5.8e-16) was correct before and after — the bug was invisible in the
synthesis and only showed up in the returned participation factors, which is exactly the kind
of defect a residual check cannot catch.

## Bug 4 — `updating/parameters.py`, `_guess_kind`: the module's own alias table was ignored

`parameters.py` carries an `_ALIASES` table so that `density`, `stiffness`, `modulus`,
`damper`, `h`, `c` … are accepted as spellings of the canonical kinds. `_normalize_kind` uses
it; `_guess_kind` — which is what infers the kind when a parameter is given by name only, as
in the documented `as_parameters({"E1": 210e9})` form — did not. It went straight to substring
and prefix matching, so an aliased name fell through to `"generic"`, which resolves to no
model attribute and dies at apply time:

```
as_parameters({"density": 7000.0})   ->  kind='generic'
apply_parameters(model, ...)         ->  KeyError: parameter 'density': no model entity
                                         matched kind='generic' target=None
```

The fix checks the alias/kind table for an exact match first and only then falls back to the
substring guessing, which is still needed for decorated names like `E_beam`. Afterwards
`density -> rho`, `stiffness -> spring_k`, `modulus -> e`, and applying `{"density": 7000.0}`
to a model writes `rho = 7000.0`. Every name that already resolved correctly still resolves to
the same kind (`E`, `E1`, `rho`, `t`, `k`, `A`, `nu`, `thickness`, `young`,
`youngs_modulus`, `mass`, `area`, `spring_k`, `damper_c` all unchanged).

## Bug 5 — `updating/responses.py`, `_mac_matrix`/`mac_vector`: a 1-D mode shape was read as a row of single-DOF modes

The local MAC helper started with `a = np.atleast_2d(np.asarray(a))` and *then* tested
`if a.ndim == 1: a = a[:, None]`. That test can never fire after `atleast_2d`, so the
column-promotion the author intended never happened, and `atleast_2d` promotes a length-n
vector to shape `(1, n)` — a single-DOF measurement of n modes rather than one n-DOF mode
shape. Every off-diagonal MAC between two single-DOF "modes" is 1, so:

| call, two 6-DOF shapes with true MAC 0.9854370 | before | after |
|---|---|---|
| `mac_matrix(v1, v2).shape` | `(6, 6)` | `(1, 1)` |
| `mac_vector(v1, v2)` | `[1, 1, 1, 1, 1, 1]` | `[0.9854370]` |
| `pair_by_mac(v1, v2)` | 6 spurious pairs, all MAC 1.0 | one pair, MAC 0.9854370 |

The canonical `femtools.correlation.mac_matrix` returns `(1, 1)` for the same input, so this
local copy was also silently diverging from the package it mirrors. Both helpers now route
through one `_as_mode_columns` promotion. The 2-D path is untouched and still agrees with
`correlation.mac_matrix` exactly.

**`updating/updater.py`** — `wls`, `ls`, `gauss-newton`, `bayesian`, `minimum-variance`,
`analytic` and `semi-analytic` all recover the 10 % beam error (6.5e-10 for the least-squares
family, 1.5e-11 for `bayesian` with a loose prior). A zero response weight correctly excludes a
50 %-corrupted target (6.3e-08 error). A tight prior (`prior_std=1e-4`) pins the answer at the
prior `[1.0, 1.0]` and a loose one (`1e4`) recovers `[1.1, 1.0]`, i.e. the prior term is
weighted the right way round. Bounds are honoured on an infeasible request. Increasing
`regularization` shrinks the step monotonically without flipping its sign
(`lam=0 -> [1.1, 1.0]`, `lam=10 -> [1.068, 1.027]`).

**`updating/force_id.py`** — `tikhonov_solve`, TSVD and `pinv` agree on well-conditioned data;

**`updating/selection.py`** — `efi`, `qr` and `forward` agree on the collinear doctest case,

**`optimization/topology.py`** — SIMP hits the volume fraction exactly (mean density 0.300000

**`mpe/`** — the H1/H2 identity, the Welch spectra against SciPy, MIMO H1/H2, ridge
