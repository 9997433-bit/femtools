## Method

Built a 19-case reproduction battery (`/tmp/r5f2/repro.py`) that feeds
**doc-conformant** content — MSC punch layout for `pch.py`, and blocked/
unblocked records exactly as specified in the official ANSYS *CDWRITE (CDB)
File Format* chapter (v24.2 help, fetched and used as the reference for
NBLOCK/EBLOCK/ETBLOCK/RLBLOCK/R/SECBLOCK field layouts) — and checks the
parsers against their own documented contracts. Only failures demonstrated
by the battery were fixed; everything else was left alone.

## Result: pch.py — no reproduced bugs, unchanged

All punch cases pass on the existing code: write/read round-trip through
the solver-flavoured result (`dof_map` path), MSC-style tolerant read
(sequence numbers, 6-decimal fields, Fortran `D` exponents, `S` scalar
points), complex-block and `$DISPLACEMENTS` skipping, negative-eigenvalue
clamp to 0 Hz, and the complex-shape write refusal. `pch.py` and
`drivers/` (protocol only) are byte-identical to before.

## Result: cdb.py — six reproduced bugs, all fixed

1. **ETBLOCK crashed on its only documented format** `(2i9,19a9)`
   (`CdbError: unsupported format item '19a9'`): `_parse_format` had no
   `a` (alphanumeric) descriptor — but ETBLOCK carries KEYOPTs as `19a9`
   text fields per the ANSYS spec. Fix: `a` descriptors are parsed and
   sliced as string fields; the two leading `i9` fields (type, element
   name number) feed `et_map` as before.

2. **`EBLOCK,...,COMPACT` was silently misparsed.** ANSYS defines COMPACT
   records as *field 1 = element number, fields 2+ = node numbers*, with
   attributes taken from the current TYPE/MAT/REAL/SECNUM. The reader
   applied the "(blank)" field layout instead, so node numbers were
   consumed as etype/real/mat and the element came out with wrong type
   and wrong connectivity (a HEX8 block produced a bogus TET4 on nodes
   5-8). Fix: dedicated COMPACT branch plus tracking of the
   `TYPE`/`MAT`/`REAL`/`SECNUM` current-attribute commands (defaults
   1/1/1/0), verified including a 20-node SOLID186 spanning two
   continuation lines.

3. **The archive form of the `R` command crashed the reader**
   (`CdbError: cannot parse integer 'UNBL'`). CDWRITE writes
   `R,<rev>,NSET,LOC,STLOC,V1,V2,V3` (rev = `R5.0` in old files, `UNBL`
   in new ones; `LOC`/`STLOC` address slots in the constant table). Fix:
   the revision token is skipped and the `LOC` style places `V1..V3` at
   `STLOC`; the interactive `R,NSET,V1..V6` style is unchanged
   (regression-checked).

4. **A short blank-format EBLOCK record swallowed the next record.** The
   continuation heuristic read more lines whenever fewer node ids than
   the element's *maximum* ANSYS node count were found — so two BEAM188
   records without orientation nodes collapsed into one element (the
   second record became "continuation nodes" of the first and was lost).
   Fix: per the spec, a record spills onto the next line **only when the
   previous line was full**; `_read_extra_nodes` now gates on that (and
   still stops at terminators/commands). Applied to blank and COMPACT;
   the SOLID key keeps trusting its explicit node-count field, now
   counted over node *fields* (zero placeholders included) instead of
   nonzero ids.

5. **BEAM3 real constants misread: `Iy` got the stress-recovery HEIGHT.**
   BEAM3 (2-D) has R = AREA, IZZ, HEIGHT — the reader applied BEAM4's
   layout (AREA, IZZ, IYY, ..., IXX) to both, so `Iy` received a length
   (0.1 m) instead of an inertia. Fix: BEAM3 carries A and IZZ only;
   `Iy = Iz` and `J = Iy + Iz` are filled in — exactly the fallbacks the
   femtools BEAM2 element documents for missing inertias (the model
   layer requires the fields to be present, hence applied at read time)
   — with a new aggregated warning. End-to-end check: an 8-element BEAM3
   cantilever read from CDB and solved with `solve_modes` matches the
   Euler-Bernoulli first bending frequency within 3 %.

6. **`RMORE` values landed at the wrong slots after a short `R` line.**
   ANSYS defines RMORE as *always* continuing at constants 7-12 (then
   13-18), but the reader plain-appended: `R,1,AREA,IZZ,IYY` +
   `RMORE,ISTRN,IXX` put IXX at slot 5, so BEAM4's `J` (slot 8) read as
   0.0 with no warning. Fix: RMORE pads the table to the next multiple
   of 6 before appending (checked after both a 3-value and a 6-value
   `R` line).

The module docstring was updated where the contract changed (EBLOCK key
handling, both `R` forms, the BEAM3 row of the element mapping table).

## Not bugs (verified, left alone)

* NBLOCK fixed-column slicing, `N,UNBL,LOC,-1` / `N,R5.3,...` trailers,
  blank trailing coordinates ("only the last nonzero value is output").
* SOLID-key EBLOCK with 20-node continuation + midside drops, ANSYS
  degeneracy collapse (I J K K M N N N -> TET4), RLBLOCK
  `(2i8,6g16.9)`/`(7g16.9)` continuation, layered SECBLOCK summing,
  MP/MPDATA, D/F grouping — all pass unmodified.
* An initial battery failure was a **fixture** error (reals written 19
  wide instead of the 21 columns `e21.13e3` demands); the parser's
  fixed-column slicing was correct.
