## The API

```python
mapped_mac(
    phi_test, xyz_test, modes, xyz_fe=None, *,
    test_map=None, tol=None, unique=False,
    dof_map=None, dofs=None, dofs_per_node=None, missing="raise", weights=None,
) -> MappedMACResult
```

The three calls that correlate a digitized test against a mesh, done once and consistently:

```python
# before
ids, dist = map_nearest_nodes(test_xyz, model, tol=0.01)
phi_a = mapped_mode_matrix(modal, ids, dofs=("x", "y", "z"))
mac = mac_matrix(phi_test, phi_a)

# after
result = mapped_mac(phi_test, test_xyz, modal, model, tol=0.01, dofs=("x", "y", "z"))
print(result.table())
```

Nothing new is computed — the result is **bit-identical** to the three-call chain (checked, and
checked again by the R9-F3 example). What the wrapper adds is the bookkeeping that is easy to get
wrong by hand: the two matrices are put on the same rows, and the node match that produced them is
kept next to the number it produced.

* **`phi_test`, `xyz_test`** — the test side. `xyz_test` is an `(n, 3)` / planar `(n, 2)` array, a
  `{id: xyz}` mapping, an `(ids, xyz)` pair or a model; everything in the result is reported in that
  order. `phi_test` is `(n_point * n_component, n_mode)` node-major in that same order.
* **`modes`, `xyz_fe`** — the analysis side, exactly as `mapped_mode_matrix` and `map_nearest_nodes`
  take them. `xyz_fe` may be omitted only when `modes` itself carries coordinates; a `ModalResult`
  does not, and the error says so instead of failing obscurely.
* **`test_map`** — DOF ordering of `phi_test`. See "the ordering trap" below; this is the parameter
  that keeps a test side which is itself a *model* honest.
* **`tol`, `unique`** go to `map_nearest_nodes`; **`dof_map`, `dofs`, `dofs_per_node`, `missing`** go
  to `mapped_mode_matrix`; **`weights`** goes to `mac_matrix` (so a mass-weighted MAC on the mapped
  row set is one keyword).

`MappedMACResult` is a dataclass, not a bare matrix, because a mapped MAC without its distances is
a number you cannot judge:

* `mac` — the `(n_mode_test, n_mode_fe)` matrix. `np.asarray(result)` and `result[i, j]` reach it
  directly, so the object drops into anything that expected `mac_matrix`'s return value.
* `nodes` — the `NearestNodeMap`, with `ids` / `distance` / `max_distance` / `rms_distance` /
  `is_one_to_one` / `n_matched` also surfaced on the result itself.
* `phi_test`, `phi_fe` — the two matrices as correlated, for a follow-up `mac_contribution` or
  `pair_modes`.
* `diagonal`, `min_diagonal`, `n_dof`, `shape`, `dofs` (`('X', 'Y', '-Z')`), and `table()`, which
  prints the diagonal, the best off-diagonal per mode, and the geometry line underneath it.

### Design points worth knowing

* **The ordering trap this closes.** On an `FEModel` the geometry and the DOF rows are *not* in the
  same order: `coordinate_table` walks `model.nodes` in **insertion** order while the DOF map is in
  **sorted node-id** order. So when the test side is itself a solved model, reading `phi_test` row
  blocks positionally against `xyz_test` silently correlates the wrong nodes — on my gate block that
  gives a diagonal of `[0.25, 0.15, 0.03, 0.23, 0.0002, 0.22]` instead of 1. `mapped_mac` therefore
  gathers the *test* rows by `(node, component)` too — with the same `_mapped_rows` machinery the FE
  side uses — whenever `phi_test` carries a DOF map (or `test_map` is given) **and** `xyz_test`
  carries node ids. A bare coordinate array carries no ids, so that case stays positional, which is
  what a real digitized point cloud is. This is the one place where the wrapper is more than the sum
  of the three calls, and it is why the gate is a two-argument call rather than a manual re-index.
* **A sign belongs to one side only.** `dofs=("x", "y", "-z")` describes a reversed accelerometer,
  i.e. a *relation* between test and model, so the flip is applied to the analysis rows (as
  `mapped_mode_matrix` does) and never to the test rows. Flipping both would cancel exactly and the
  option would be a no-op; as implemented, a genuine sign error shows up as a lowered MAC, and
  reversing the sensor *and* the data cancels — both pinned.
* **`missing=` moves both sides together.** `'drop'` drops the unmatched points from the test matrix
  as well (that mask is precisely what the wrapper knows and the caller would have to reconstruct);
  `'zero'` keeps the test rows against zeroed analysis rows, which lowers the MAC honestly rather
  than hiding the gap. `'drop'` also accepts a `phi_test` the caller already restricted.
* **Row-count mismatches name the fix.** The default `dofs` is the component set the DOF map holds —
  six on a normal model, while test data is usually three translations. Rather than guess, the error
  reads: `phi_test has 24 rows but the mapped analysis matrix has 48: 8 test points x 6 components
  (X, Y, Z, RX, RY, RZ) ... 3 rows per test point would fit, so pass dofs=("x", "y", "z")`.
* **Nothing is interpolated or re-scaled**, so the unit diagonal on a relabelled copy is exact rather
  than approximate, and a bad match remains a geometry problem visible in `result.nodes`.

### Internal refactor (behaviour-preserving)

`mapped_mode_matrix` was split into `_gather_plan` (resolve the mode matrix, its DOF map and the
components) and `_gather_mapped` (the row gather), so `mapped_mac` can reuse the *same* resolved
components for the test side instead of re-deriving them. `mapped_mode_matrix` is now those two
calls and nothing else. I A/B'd it against a verbatim copy of the R8 body over 40 random cases ×
both code paths (positional and DOF-map, real and complex, all three `missing` policies, permuted
and partial `dofs`): **bit-identical output and dtype in every case**, plus the whole test suite and
the R8 probe.

### The gate, measured in process

```python
"""R9-O3 gate: two translated copies of the same block -> mapped-MAC diag 1."""
import numpy as np
from femtools.core.model import FEModel
from femtools.correlation.dofmap import mapped_mac
from femtools.fea.eigen import solve_modes

EDGES = (1.0, 1.3, 1.7)   # unequal edges: six distinct clamped modes, no degeneracy
CORNERS = [(x, y, z) for z in (0.0, EDGES[2]) for x, y in
           ((0.0, 0.0), (EDGES[0], 0.0), (EDGES[0], EDGES[1]), (0.0, EDGES[1]))]

def block(name, shift=(0.0, 0.0, 0.0), ids=range(1, 9)):
    m = FEModel(name=name)
    ids = list(ids)
    for nid, xyz in zip(ids, CORNERS, strict=True):
        m.add_node(id=nid, xyz=np.asarray(xyz) + np.asarray(shift, dtype=float))
    m.add_material(id=1, type="isotropic", E=70.0e9, nu=0.3, rho=2700.0)
    m.add_property(id=1, type="solid", material_id=1)
    m.add_element(id=1, type="HEX8", nodes=tuple(ids), property_id=1)
    for nid in ids[:4]:
        m.add_spc(nid, [True] * 6)
    return m

fe = block("fe")
fe_modal = solve_modes(fe, n_modes=6)
rng = np.random.default_rng(20260828)
worst = 0.0
for _ in range(8):
    shift = rng.uniform(-0.45, 0.45, size=3) * np.asarray(EDGES)
    ids = rng.permutation(np.arange(101, 109)).tolist()      # renumbered copy
    test = block("test", shift=shift, ids=ids)
    result = mapped_mac(solve_modes(test, n_modes=6), test, fe_modal, fe)
    assert result.is_one_to_one
    assert abs(result.max_distance - np.linalg.norm(shift)) < 1e-14
    worst = max(worst, float(np.max(np.abs(result.diagonal - 1.0))))
print(f"8 translated + renumbered copies: max |diag(MAC) - 1| = {worst:.3e}")
print(result.table())
```

### Two constraints on the gate geometry, both real

1. **Unequal edges, as the brief says.** A literal 1×1×1 cube clamped on one face has repeated
   eigenvalues (570.971 Hz twice, 2160.478 Hz twice), and inside a repeated eigenvalue the individual
   eigenvectors are not unique — translating the mesh perturbs the assembled matrices at the ULP
   level, which rotates the basis LAPACK returns. Measured on the cube, the diagonal is
   `[0.683, 0.683, 1.0, 1.0, 0.990, 0.990]`: exactly 1 for the two non-degenerate modes, split within
   each degenerate pair, and **each degenerate 2×2 block sums to exactly 1.0 per column** — the
   mapped shapes span the same subspace, nothing was lost by the gather. That is a property of
   degenerate eigenproblems, not of `mapped_mac`. The 1 × 1.3 × 1.7 block has six distinct
   frequencies and no such ambiguity.
2. **The translation must stay under half an edge, or be undone first.** Plain nearest-node matching
   is geometric: translate the test copy by 25 edge lengths and *every* test point's nearest FE node
   is the same corner, so the correlation is meaningless (correctly reported as `is_one_to_one =
   False`, `max_distance > 25`). Either keep `|t_i| < edge_i / 2`, as the gate above does, or bring
   the clouds into one frame with `align_geometry` first — the end-to-end check does that with a 37°
   rotation and a 12-unit offset and still lands on `max|diag − 1| = 0.0`. Anyone writing an
   acceptance test for a *large* offset must include the `align_geometry` step.
