# 1. `psd_response(..., base_accel=)`

## The formulation, and why it needs a participation vector

A vibration specification is an *acceleration* of the support, not a force. Splitting the
motion into the rigid ride plus the deformation, `u_abs = r x_g + u`, turns the support
motion into an ordinary force on the relative coordinates:

    M u'' + C u' + K u = -M r a_g(t)

so the excitation is the force PSD of `-L a_g` with `L = (M r)` restricted to the excited
DOFs. That is the whole content of the new keyword — no new solver, the same
`H S H^H` contraction, and the force-PSD path is byte-for-byte the code it always was.

Two consequences drove the signature:

* **A single rigid support is perfectly coherent across every DOF it drives.** Reading
  `base_accel` per *input DOF* the way `force_psd` is read would make a scalar mean "each
  bolt shakes independently", which is never what a shaker does. So the leading dimension
  of `base_accel` counts **support directions** (`n_dir`, the number of columns of
  `base_participation`, one by default) and the force spectrum it implies is the rank-one
  `L S_aa L^H`. All six broadcast shapes of `force_psd` still apply, over that axis;
  independent supports are the multi-column case and are additive (checked: exact).
* **`L` cannot be guessed from a modal model.** `psd_response` sees modes and frequencies,
  never `M`, so the participation block is an argument. It defaults to ones, which is
  exactly the SDOF / unit-modal-mass case the closed forms assume, and for a lumped-mass
  model it is literally the mass at each excited DOF.

```python
psd_response(modal, base_accel=S_a, freq_hz=f, damping=0.02,
             inputs=excited, outputs=[tip], base_participation=(M @ r)[excited])
```

## Relative or absolute

Documented and switchable, defaulting to **relative** because that is the coordinate the
stress lives in:

| `base_absolute` | what comes back | transfer |
|---|---|---|
| `False` (default) | deformation relative to the moving support | `G = -H L` |
| `True` | what an accelerometer on the structure reads | `G = -H L + r * ride(w)` |

`ride(w)` converts the support acceleration into the requested response kind: `1` for
accelerance, `1/(i w)` for mobility, `-1/w^2` for receptance. The last two are singular at
`f = 0`, where a stationary acceleration spectrum says nothing at all about the
displacement of the support, so a DC line is **refused with a message naming the three
ways out** rather than returned as an infinity — the same treatment R6 gave `as_response`
and R5 gave `lower_residual`. `base_influence` is `r` restricted to the outputs and
defaults to ones.

On an SDOF with `L = r = 1` this collapses to the textbook transmissibility
`(w_n^2 + 2 i zeta w_n w) / (w_n^2 - w^2 + 2 i zeta w_n w)`, reproduced line by line to
**3.1e-13** relative.

## Measured against the closed forms

For a flat one-sided `S_a` and a mass-normalised mode the exact infinite-band answers are

    sigma_rel = sqrt(S_a / (8 zeta w_n^3))                          = miles_rms(f_n, zeta, S_a)
    sigma_abs = sqrt(pi f_n S_a / (4 zeta)) * sqrt(1 + 4 zeta^2)

The `sqrt(1 + 4 zeta^2)` on the second is the damper's own force, which the usual quotation
of Miles' equation drops; it is 0.08 % at 2 % damping. I derived it from the standard `I_2`
spectral integral and then confirmed the number by piecewise `scipy.integrate.quad`
(`2.9499555017208174` against the formula's `2.949955501720816`) before comparing anything
to the code.

`f_n = 25 Hz`, `zeta = 0.02`, `S_a = 3e-3`:

| quantity | grid | `psd_response` | closed form | rel. error |
|---|---|---|---|---|
| relative displacement | the test suite's `_band()` | `6.955379427369963e-05` | `6.955379331840876e-05` | `1.4e-08` |
| absolute acceleration | same | `1.7174540037777901` | `1.717543449733024` | `5.2e-05` |
| absolute acceleration | 20 k geometric lines to `1e4 f_n` | `1.717543489786792` | " | `2.3e-08` |
| absolute acceleration | 80 k lines | `1.7175434505180318` | " | `4.6e-10` |

The `5.2e-05` row is not an error in the transfer, it is the trapezoid on that grid: the
absolute-acceleration spectrum decays only as `1/w^2` (the damper term), so it needs a
wider, better-resolved band than the relative one, and it converges at the documented
`O(df^2)`. Worth knowing before quoting an absolute RMS; it is now in the module docstring.

## Measured against things that are not closed forms

**Bit-identity with the force path.** With `L = 1` the relative-response PSD equals the
force-PSD result for `S_ff = S_a` to the last bit (`max |difference| = 0.0`). That matters
because the existing `@pytest.mark.slow` Wiener-Khinchin test validates the force path
against a simulated time history, so the relative base path inherits that validation
exactly.

**A time simulation that exercises `L = M r`.** 2-DOF chain (`M = diag(2, 3)`,
`14.567 / 42.594 Hz`), 5 % damping, 400 s at 4 kHz of discrete white base acceleration
driven through the equivalent force `-M r a_g`:

| DOF | simulated RMS | predicted RMS | error |
|---|---|---|---|
| 0 | `1.70535e-03` | `1.69083e-03` | 0.86 % |
| 1 | `2.91720e-03` | `2.89224e-03` | 0.86 % |

That is inside the statistical scatter of a record this long, and it is the check that
catches a wrong mass in the participation vector, which no closed form on a unit-mass SDOF
can see.

**Effective-mass sum rule on a real model.** BEAM2 cantilever, 10 elements, 66 DOFs,
`r` = rigid `+uz`, `L = M r`, 40 modes:

| | value |
|---|---|
| `r^T M r` | `4.710000 kg` = `rho A L` exactly |
| sum of `(phi_r^T M r)^2` over 40 modes | `4.560361 kg` (96.82 %) |
| first mode, 16.710 Hz | `2.88759 kg` = **61.31 %** |
| third mode, 104.725 Hz | `0.88689 kg` (18.83 %) |

61.31 % is the textbook cantilever first-mode effective mass fraction (0.6131). A
participation vector built the wrong way — mass omitted, or the SPC'd root included as a
deforming DOF — does not land on that number.

**The cantilever answer itself**, flat `0.05 (m/s^2)^2/Hz`, 2 % damping, 0.5-501 Hz:

| | |
|---|---|
| tip relative displacement RMS | `8.139076e-04 m` (3-sigma `2.442e-03 m`) |
| single-mode closed form `phi_tip * Gamma_1 * sqrt(S_a/(8 zeta w^3))` | `8.137012e-04 m` (0.025 % apart) |
| tip absolute acceleration RMS | `1.973335e+01 m/s^2` |
| relative upcrossing rate | `17.157 Hz` against `f_1 = 16.710 Hz` |
| absolute tip PSD at 0.836 Hz | `5.0388e-02` against `S_a = 5.0e-02` |

The last row is the physical statement the relative/absolute switch exists for: well below
the first mode the tip simply rides with the shaker (absolute PSD is the input, relative
response is `7.5e-07`, six orders down).

## Validation, and what the force path did not lose

`force_psd` became keyword-defaultable (`None`) so `base_accel=` can stand alone, and
exactly one of the two must be given — they are two descriptions of one excitation, not
two excitations. `base_participation`, `base_influence` and `base_absolute` are refused
next to a force PSD instead of being silently ignored, which is the R6 lesson about
`assemble=`. `_as_force_psd` grew a `name` argument only so its diagnostics say
`base_accel` when that is what the caller passed; every existing message and every existing
shape rule, including the documented `n_in == n_freq` collision, is unchanged, and the
three error-matching assertions in `tests/test_random_psd.py` still match.

Eleven rejection paths were probed, all raising with the argument named:

```
neither / both given             exactly one of force_psd and base_accel is required
base_participation w/o base      ... only applies to a base_accel excitation
DC line + absolute receptance    ... unbounded at f = 0; drop the DC line, ask for
                                 response='accelerance', or leave base_absolute off
base_accel = -1.0                base_accel has a negative auto-spectrum
1-D participation, wrong length  needs one entry per DOF (1 here), got 2
influence direction mismatch     base_influence has 3 support directions but the
                                 excitation has 2
```

An already-computed `FRFResult` drives the base path exactly as it drives the force path
(identical to the from-scratch call). `meta` gains `excitation`, `base_frame`
(`"relative"` / `"absolute"`), `n_base_dir` and the resolved `base_participation`.

# 2. `femtools.dynamics.superelement` — `dump_cms` / `load_cms`

```python
from femtools.dynamics.superelement import dump_cms, load_cms, Superelement

dump_cms(result, path, *, compress=False, meta=None) -> Path | file object
load_cms(path) -> CraigBamptonResult | FreeCMSResult | Superelement
```

Also exported from `femtools.dynamics` (`Superelement`, `dump_cms`, `load_cms`).

**The class is restored, not just the arrays.** A Craig-Bampton component comes back as a
`CraigBamptonResult` — with `fixed_freq_hz`, `constraint_modes` and `fixed_modes`, so
`solve_modes()`, `expand()`, `n_modal` and `n_boundary` all still mean what they meant —
and a Rubin or MacNeal component as a `FreeCMSResult` carrying `free_freq_hz`,
`residual_freq_hz`, `residual_flexibility` and its `method`, so `interface_flexibility()`
and `free_interface_assembly` accept it directly. That is what "usable for a second eigen
solve" has to mean in practice: the loaded object is not a special case anywhere
downstream.

Anything else exposing `K`, `M` and `T` — a duck-typed reduction, a plain mapping — is
written too and comes back as `Superelement`, the minimum object that can still be expanded
and eigen-solved. Its solve goes through the same semidefinite path `macneal` needs, so a
massless residual block is condensed rather than crashing.

**Bit-identical, and measured as bytes.** Everything is stored as raw `float64` in an
uncompressed-by-default `npz`; the check is `tobytes()` equality, not `allclose`:

| source | class back | `K`,`M`,`T` bytes equal | `solve_modes().freq_hz` `array_equal` |
|---|---|---|---|
| `craig_bampton(Ka, Ma, [19], 6)` | `CraigBamptonResult` | yes | yes (7 modes, `f1 = 1.987596234`) |
| `rubin(Kb, Mb, [0], 6)` | `FreeCMSResult` | yes | yes (7 modes) |
| `macneal(Kb, Mb, [0], 6)`, `compress=True` | `FreeCMSResult` | yes | yes (6 modes; the massless residual is condensed, as it should be) |
| hand-rolled object / mapping | `Superelement` | yes | matches the source component |

`compress=True` (`savez_compressed`) changes the file size, not the bits: `4291 B` against
`6434 B` for the same Rubin component, and the loaded arrays compare equal either way.

**Round-tripping does not perturb an assembly.** Two Rubin halves of the 40-mass chain
written out, read back and coupled through `free_interface_assembly` give frequencies
`np.array_equal` to the same assembly built in memory — `[0.98167455, 2.94354801,
4.90100631, ...]`. That is the property that makes the file worth writing: a reduced
component that shifted in the last bits between the run that produced it and the run that
consumes it cannot be compared with anyone else's.

**Refusals.** `dump_cms` names the missing field (`K`, `M` or `T`) and checks that `K`/`M`
are square and equally sized and that `T` has one column per reduced coordinate, so a
mis-shaped basis is caught at write time rather than at the next eigen solve. `load_cms`
refuses an archive without the `femtools.dynamics.superelement/1` tag (a plain
`np.savez(f, K=...)` is rejected by name), an unknown `kind`, and an archive that claims a
class but has lost one of its fields.

**Two deliberate choices.** A path without an `.npz` suffix gets one *here* rather than
inside `np.savez`, and the resolved `Path` is returned, so the caller is never left holding
a name that does not exist — `dump_cms(cb, tmp/"cb")` returns `.../cb.npz`. And `meta`
travels as JSON with a numpy-aware fallback, which means it is provenance, not data: tuples
arrive as lists, and anything JSON cannot express arrives as its `str`. Both are documented
on the functions. `load_cms` adds `meta["loaded_from"]`. Open binary file objects work on
both sides and are returned unchanged.

The format is one array per field plus a tag, `allow_pickle=False` throughout, so anything
that reads numpy archives can read a femtools superelement without importing femtools.
