## The gap that round 2 closes

Round 1 built the correlation and pretest packages against *arrays plus a DOF map*, and the map was
documented as "whatever `AssemblyResult.dof_map` turns out to be". Once the FEA kernel landed, the two
sides did not actually meet:

* `femtools.fea.dofmap.DofMap` is not a `Mapping`, so `DOFMap.from_mapping` fell through to its
  sequence branch, iterated the node ids and raised `cannot parse DOF label 1: no component`.
* Component numbering disagrees. The kernel is **zero based** (`femtools.fea.protocols.DOF_LABELS =
  ux..rz`, `normalize_dof` returns `0..5`), the correlation package is **one based** (`1..6 = X..RZ`).
  `FEModel.dof_map()` returns `{(node, 0..5): eq}`, and `parse_component(0)` raised
  `component 0 out of range 1..6`.

Both are now handled, plus the surrounding conveniences that make the workflow read the way the module
docstrings claim it does.

### DOF map sources, all equivalent

All six of these now produce the identical 1-based `DOFMap`, and `d.index_of((node, comp))` was checked
against `modal.dof_map.index(node, comp - 1)` for every node and component of a test model:

```python
as_dofmap(modal)              # ModalResult
as_dofmap(modal.assembly)     # AssemblyResult
as_dofmap(modal.dof_map)      # femtools.fea.dofmap.DofMap
as_dofmap(model)              # FEModel  (dof_map is a *method* -> called)
as_dofmap(model.dof_map())    # {(node, 0..5): eq}
as_dofmap(model.dof_index())  # ((node, 0..5), ...)
```

**Base detection.** Integer components are one based unless a `0` appears, which the `1..6` convention
cannot produce. Every complete kernel map contains `ux`, so detection is unambiguous there; a partial
zero based map that happens to omit `ux` (say only `ry, rz`) needs the explicit
`from_mapping(..., base=0)`, which is documented on the parameter. Labels (`"12Z"`, `"12:-Z"`, `"7RY"`)
are always one based and never shifted.

### Translational slice

```python
modal = solve_modes(model, n_modes=20)
em = effective_mass(modal, modal.M, dof_map=modal, coords=node_coordinates(model, modal))
targets = select_target_modes(em, f_max=200.0, mass_fraction=0.85, directions=("TZ",))

cand = translational_dofs(modal, components="z", mode_index=targets, coords=model)
sensors = effective_independence(cand.phi, 5, candidate_dofs=cand.dofs)
picked = cand.take(sensors.index)          # labels, nodes, coordinates of the chosen sensors
```

`CandidateSet` carries `phi` (the `(n_candidate, n_target)` partition), `dofs` (global DOF numbers of
its rows, so an `EFIResult` comes back indexing straight into `modal.modes`), `dof_map` (labels/nodes/
components), `mode_index`, `freq_hz` of the target columns and, when coordinates are reachable,
`coords` per candidate. It behaves like its `dofs` array (`IdSequenceMixin`), and `take()` re-slices it
with a selection result.

`active_only=True` (default) drops rows the FE model cannot move: DOFs outside `AssemblyResult.free_dof`
(SPC'd, massless, fictitious drilling) and rows exactly zero in every target mode. Those have zero
effective independence and only dilute the ranking; the count is reported as `CandidateSet.dropped`.
Also available: `components` (labels or ids, `None` for all), `nodes`, `exclude` (whole nodes or
individual DOF keys), `dof_map`/`modes` overrides for data that never went through the kernel.

`node_coordinates(model, dof_map)` reorders a model's nodal coordinates onto a DOF map (per node or per
DOF). A `ModalResult` cannot supply coordinates — the kernel keeps node *ids* but not geometry — so the
model has to be passed for `coords`; `missing="none"` makes that silent rather than an error.

## Vectorization

Every addition is array code; the only Python loops left are the inherently sequential eliminations
(EFI, MAC elimination) and the per-item label parser, which now runs only when the components are not
already an integer array.

| Operation (20 000 nodes, 120 000 DOF) | Round-1 style | Round 2 | Note |
|---|---|---|---|
| Build a `DOFMap` for the model | 59.6 ms | **1.1 ms** | vectorized parse; duplicate check by sorted codes; the `(node, comp) -> row` dict is built lazily and often never |
| `common()` model vs 40-channel test map | 22.7 ms | **0.9 ms** | one `argsort` + `searchsorted` on packed `node*8 + comp` codes instead of one dict lookup per DOF |
| `DOFMap.from_mapping(modal)` | (raised) | 3.6 ms | |
| `translational_dofs(modal, mode_index=…)` | — | 14.0 ms | one fancy-index copy of 60 000 x 8 |
| `translational()` slice alone | — | 0.12 ms | |

Both fast paths were checked against the round-1 implementations on the same data: `common()` returns
bit-identical index arrays, and the packed-code path falls back to the dict when node ids exceed 2^59
(unreachable in practice, covered by a unit probe).

## Compatibility

Additive only. `align_modes(phi_a, map_a, phi_b, map_b)` keeps its positional signature; the maps may
now be `None`, which takes them from the corresponding mode object, so
`align_modes(phi_test, test_map, modal)` is the new short form. `mass_loading`'s `freq_hz` became
optional (second positional, unchanged for existing callers). Everything else is new names.

One behavioural nuance worth knowing: `mac_matrix(a, b)` takes the exact-symmetry branch (bit-exact
`1.0` diagonal) whenever the two operands compare equal element-wise, which now also fires when the same
`ModalResult` is passed twice. Note this is *not* the identity matrix for a model with repeated or
rigid-body modes: mass-orthogonal modes are not Euclidean-orthogonal, so the unweighted off-diagonals
are legitimately non-zero — use `cross_orthogonality(phi, None, M)` for the orthogonality check.

## Notes for other agents

* **F4 / CLI.** `femtools pretest` currently calls `effective_independence(np.asarray(modal.modes),
  n_sensors=…)`, which ranks *all* DOFs including rotations and SPC'd rows, and reports bare row
  indices. Two lines make it a real pretest and give labelled output:

  ```python
  cand = translational_dofs(modal)                 # femtools.pretest
  ranked = effective_independence(cand.phi, n_sensors, candidate_dofs=cand.dofs)
  labels = cand.take(ranked.index).labels          # ['12Z', '31Z', ...]
  ```

* **Updating / dynamics.** `DOFMap.from_mapping` accepts a `ModalResult`, an `AssemblyResult`, a kernel
  `DofMap` or an `FEModel` interchangeably, so response-DOF bookkeeping ("node 12, direction Z" ->
  global row) is `as_dofmap(modal).index_of((12, "z"))` — the same call whether the caller holds the
  model or the result.
* Global DOF row numbers are the ids I hand around (`CandidateSet.dofs`, `EFIResult.dofs` when fed from
  it). They index directly into `ModalResult.modes` and into the assembled `K`/`M`, which is what
  `restrict(modal.M, dofs)` needs for a mass-weighted cross-orthogonality on the test DOF set.
* Still deliberately absent: a TAM reduction (Guyan/IRS/SEREP) to build a reduced test mass matrix —
  that belongs in `fea`/`dynamics`, not here. Until it exists, `restrict(M, sensor_rows)` is the
  pragmatic stand-in used above.
