Signature, now pinned by test:

```python
apply_mpc(model, *, rbe2=None, rbe3=None, dof_map=None, dofs_per_node=6, index=None)
```

`None` reads the model's own table, `()` leaves that card type out, anything

## What changed, and what deliberately did not

**Nothing numerical.** `RBE2` is still the rigid weld
`u_m = u_n + theta_n x r`, `RBE3` still `u_d[c] = sum_i w_i u_i[c] / sum_j w_j`
one component at a time and reading **no coordinates at all**, and
`ConstraintTransform.from_rows` still resolves chains before building `G`. The
HEX8 / MITC4 / drilling / enforced-displacement goldens are re-measured
unchanged below.

Three things did change, all of them contract rather than content:

1. `fea/mpc.py` — the module docstring gained a *One composer* section stating
   the frozen shape: `apply_mpc` builds the rows, `apply_rbe2` / `apply_rbe3`
   are it with the other table set to `()`, and that is *why* the bit-identity
   claim holds (same rows, same insertion order, therefore the same CSR
   arrays). `apply_mpc` gained a full parameter docstring; the two wrappers say
   in one sentence that they are wrappers.
2. `fea/mpc.py` — `apply_mpc` now rejects a bare `ndarray` / sparse matrix or a
   ready-made `ConstraintTransform` in `rbe2=` / `rbe3=` with a `TypeError`,
   the way `resolve_mpc` already did for `mpc=`. Before, a matrix reached the
   record reader and came back as `RBE2 0: no independent node (looked for
   ('independent', ...))`, which is a true statement about a wrong question.
3. `fea/verification.py` — new `mpc_mixed_chain` case (plus
   `MPC_CHAIN_DIRECTIONS`), the reproducible free-free measurement of the two
   card types chained in either direction. It is the round's acceptance case
   and is quoted below rather than re-derived inside the test module.

## `mpc_mixed_chain`

A closed `BEAM2` triangle — a frame, so all six components of all three
vertices carry stiffness and inertia — with a 2.5 kg mass hung two constraints
away:

* `direction="rbe2_on_rbe3"`: node 4 is the reference grid of an `RBE3`
  interpolating the three vertices, node 5 is welded to node 4 by an `RBE2`,
  and the mass sits on node 5. A rigid arm on a node that is only an average.
* `direction="rbe3_on_rbe2"`: the reverse — node 4 is welded to vertex 1, and
  node 5 is the reference grid of an `RBE3` whose independents include that
  rigid node.

Where the mass is delivered is analytic and is the physically interesting part.
An `RBE2` reproduces a rigid body motion exactly and moves the mass by its own
lever; an `RBE3` carries it to the **weighted centroid** of its independents
(the R8-O1 result). Composed, the delivery point is
`sum_i w_i x_i + (x_5 - x_4)` in the first direction and `sum_i w_i x_i` over
the `RBE3`'s independents — one of which is the rigid node — in the second.
The case reports the reduced rigid body mass error against the bare triangle
plus a point mass sitting exactly there.

## Notes for other agents

* `apply_mpc(model, rbe2=<matrix>)` now raises `TypeError` instead of the old
  "no independent node" `ValueError`. Only a caller that was passing a matrix
  where records belong is affected, and `assemble_km(mpc=<matrix>)` already
  raised `TypeError` with the same wording (`not a bare matrix`).
* The order of the product matters and is worth knowing when reading `G`:
  composing is `G_outer @ G_inner`, where the outer card is the one whose rows
  reference the other's dependents. For `RBE2`-on-`RBE3` that is
  `G_rbe2 @ G_rbe3`; for `RBE3`-on-`RBE2`, `G_rbe3 @ G_rbe2`. The composer
  produces either exactly, so a reader does not have to know.
* `mpc_mixed_chain(direction, weights=..., mass=..., radius=..., arm=...)` and
  `MPC_CHAIN_DIRECTIONS` are available to R9-G1/G2 and to the docs; the keys
  are `zero_modes`, `first_elastic_hz`, `free_dof`, `dependent_dof`,
  `constraint_stiffness`, `idempotency`, `rigid_mass_error` and
  `delivered_x/y/z`.
* For R9-F1: `apply_mpc` imports on this tree and is already in
  `femtools.fea.__all__`; the top-level `_EXPORTS` entry is parent glue, not
  mine, and `src/femtools/__init__.py` is untouched here.
