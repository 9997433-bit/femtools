# R2-O4 — Updating, Optimization, MPE, RBPE (round 2)

Scope: `src/femtools/updating/**`, `src/femtools/optimization/**`,
`src/femtools/mpe/**`, `src/femtools/rbpe/**`. Five files changed, all inside
those paths. No git command was run.

## 1. Headline

`update_model` now works against a real `femtools.core.model.FEModel` solved by
`femtools.fea.eigen.solve_modes`, confirmed on 16 separate checks. The 10 %
Young's-modulus recovery case lands at **7.9e-8 %** parameter error against a
2 % bar, and stays at **0.68 %** with 0.5 % noise on the measured frequencies.

The round-2 API work turned out not to be about the tests — `tests/test_doe.py`,
`tests/test_topology.py` and `tests/test_updating.py` were already green and
still are. It was about the *other* callers: the repo's own acceptance example
`examples/update_youngs.py` and the `femtools update` CLI command both called
`update_model` with a convention it did not support, and both failed outright.
They now run end to end.

## 2. `update_model` against the real FEA kernel

A 10-element `BEAM2` cantilever split into two material regions, truth
`E1 = 1.10 E0`, `E2 = 0.95 E0`, five target frequencies from `solve_modes`:

| check | result |
|---|---|
| parameter error, implicit solver | **7.874e-8 %** (bar: 2 %) |
| parameter error, explicit `solver=solve_modes` callback | 7.874e-8 %, bit-identical to the implicit route |
| relative RMS frequency error | 2.882e-2 → 1.593e-10 |
| iterations / response evaluations / wall time | 3 / 16 / 0.09 s |
| `result.model` re-solved through `solve_modes` vs measurement | 2.05e-10 relative |
| caller's `FEModel` after the call | unmutated |
| absolute `E` parameters in Pa (not multipliers) | 7.886e-8 % |
| `rho` parameter on the same model (truth ×1.12) | 4.7e-7 % |
| frequencies + `1-MAC` residual using real `solve_modes` mode shapes | 3.331e-8 % |
| 0.5 % frequency noise, WLS / Bayesian | **0.678 %** / 0.628 % |

The FE mode shapes come back mass-normalised over the *full* DOF space and
`assemble_km` returns full-size `K`, `M`, so `phi^T M phi = I` and
`phi^T K phi = lambda` hold directly on the solver output — which is what makes
the analytic sensitivity route below exact without any DOF bookkeeping.

Frequencies also cross-check against the analytical fallbacks: the FE cantilever
matches the Euler–Bernoulli `BeamModel` in `femtools.updating.reference` to
0.003 %, so the reference models remain valid stand-ins.

## 3. What was broken, and what I changed

### 3.1 The acceptance example did not run

`examples/update_youngs.py` — the file that encodes acceptance case 6 — called

```python
update_model(
    nominal,
    parameters=[{"type": "material", "id": 1, "name": "E", "lower": 0.5, "upper": 2.0}],
    measured={"freq_hz": f_test},
    method="analytic",
)
```

Every one of those four things was unsupported: the parameter descriptor keys
(`type`, `id`), the `measured=` keyword, and `method="analytic"`. It raised
`TypeError: unexpected keyword argument 'measured'`. Since `examples/` is not
mine to edit and the calling convention is a reasonable one, I taught the
updater to speak it.

**Entity descriptors** (`parameters.py`). `as_parameters` now accepts a
descriptor mapping where `type` names the model container, `id` the entity and
`name` the physical quantity, alongside the existing forms. `Parameter` gained a
`container` field so `{"type": "material"}` restricts the search to
`model.materials` instead of probing by kind. Unknown descriptor keys raise a
`TypeError` that lists the accepted ones rather than surfacing a raw dataclass
error, and repeated names (two materials both called `E`) are disambiguated to
`E_1`, `E_2` instead of tripping the duplicate-name guard.

One semantic decision worth flagging: **a descriptor that does not state an
explicit `value` is now interpreted as a multiplier on the model's own value,
starting at 1.0.** Bounds of `(0.5, 2.0)` on a Young's modulus only make sense
that way, and the previous reading (absolute, starting at 1.0 Pa) was never
useful. Mappings that *do* carry a `value` keep absolute semantics, so
`as_parameters({"E1": 210e9})` is unchanged.

**`measured=`** (`updater.py`). A structured alternative to `targets` that takes
`{"freq_hz": [...]}`, optionally with `modes` / `mac` / `dof_indices`, in which
case it builds the `ResponseSpec` for MAC-based mode pairing and appends the
`1 - MAC` residual entries itself (a target MAC of 1 becomes a target residual
of 0). A plain array or a plain `{name: value}` mapping still behaves as before.
Passing both `targets` and `measured` is rejected.

**`method="analytic"`** (`updater.py`). This is a *sensitivity* choice, not a
different estimator, so it now maps to weighted least squares driven by
eigenvalue derivatives. `"semi-analytic"` likewise.

### 3.2 Analytic sensitivities could not actually be used from `update_model`

Independent of the example, the analytic route was unreachable through the
updater. The iteration passed the response *callback* to `sensitivity_matrix`,
but the analytic branch differentiates the assembled `K`, `M` and so needs the
*model*; it ended up calling `apply_parameters` on a function object. The
updater now resolves the sensitivity source up front — the `FEModel`, or a
`ReferenceModel`, or the callback for the finite-difference methods — and
raises a clear error when analytic sensitivities are asked of a bare callback
instead of failing deep inside. A MAC-augmented residual silently falls back to
central differences, because the analytic formula only yields frequency rows;
a row-count mismatch is now caught explicitly rather than broadcasting wrongly.

Verified on the two-material FE beam:

| check | result |
|---|---|
| analytic vs central FD sensitivity | max rel difference **2.35e-7** |
| semi-analytic vs central FD | 2.35e-7 |
| closed form `sum_j df_i/dp_j == f_i/2` for a global E multiplier | **5.02e-12** |
| `method="analytic"` recovery | 7.872e-8 %, 3 iterations, **4** response evaluations |
| `method="wls"` (central FD) recovery | 7.874e-8 %, 3 iterations, 16 evaluations |

The analytic route cuts eigensolves by 4× but pays two extra assemblies per
parameter per iteration, so on a 40-element beam the wall times are a wash
(213 ms vs 193 ms). It wins where the eigensolve dominates the assembly, and
it is the more accurate of the two for parameters that enter linearly.

### 3.3 The `femtools update` CLI command could not load its own model

`_load_model` returns whatever the reader returns, and for `.ftproj` that is a
`Project` wrapper, not the `FEModel` — so every parameter failed to resolve with
`KeyError: no model entity matched kind='e'`. The updating package now unwraps
project-style containers (`parameters.unwrap_model`, used by `update_model`,
`modal_response_function`, `frf_response_function` and `sensitivity_matrix`), so
it accepts either the wrapper or the bare database.

Full round trip, `.ftproj` in, JSON config, `.ftproj` out:

```
converged     True          n_iter 3      message  residual below tolerance
parameters    {'E_1': 1.0999999999463879, 'E_2': 0.949999999252165}
saved E       2.30999999988e11, 1.99499999843e11   (truth 2.31e11, 1.995e11)
```

This is a workaround in my package for something that looks like a CLI/IO bug —
see §6.

### 3.4 `n_modes` is now derived from the number of targets

The default was a fixed 10. With five measured frequencies that solved ten modes
and threw five away on every single response evaluation. `n_modes=None` (the new
default) solves exactly as many modes as there are frequency targets; an
explicit `n_modes=` is still honoured verbatim, and a MAC-based residual keeps
the old behaviour since its length is not the mode count. Confirmed by counting
the `n_modes` argument reaching an instrumented solver: 3 targets → 3 modes,
`n_modes=8` → 8 modes.

## 4. DOE and topology

Both test files passed before and after; no API mismatch existed. I stress-tested
the surfaces anyway, 55 checks, all passing.

**DOE.** All four call forms of `latin_hypercube` — `(bounds, n_samples=n)`,
`(n, bounds)`, `(bounds, n)` and fully keyword — produce byte-identical plans
for a fixed seed. Exact stratification verified bin-by-bin for
`n_samples ∈ {1, 2, 3, 5, 24, 50}`, along with reseeding determinism, a
different seed giving a different plan, unit-hypercube output when no bounds are
given, `centered=True` landing on stratum midpoints, and the maximin criterion
beating uniform random on centred-L2 discrepancy. `full_factorial` reproduces
the exact Cartesian product for explicit per-dimension levels, handles level
*counts* with bounds (`full_factorial(2, bounds)` → the `2^k` corners) and mixed
counts, and rejects levels and bounds supplied together.

**Topology.** The test's exact call reproduces; beyond it I swept five
mesh/volume-fraction/filter/boundary-condition combinations plus `max_iter ∈
{1,2,3}` and confirmed the volume constraint, the density box and finiteness
hold in every case; passive void and solid regions are enforced (1.0e-3 and
1.000); two simultaneous load cases run; `(node, dof, value)` load triples work;
and the run is bit-for-bit deterministic. The 60×20 MBB benchmark still gives
compliance **203.31** at exactly 0.500000 volume fraction, matching the
published 99-line reference.

Two small additions, both because `docs/algorithms/optimization.md` documents
them and they cost nothing: `loads=` / `spcs=` as aliases for `forces=` /
`fixed_dofs=` (passing both raises), an accepted-and-ignored `seed=` for
signature compatibility, and `TopologyResult.compliance_history` as a plain
array. `TopologyResult` also now answers to all four density attribute names
that `tests/test_topology.py` enumerates in its `_density_array` probe
(`density`, `densities`, `x`, `design`), so the test passes on any of its
branches rather than only the first.

## 5. MPE against real FE data

`femtools.dynamics` exists now, so the modal estimators were checked against an
FRF synthesized by `modal_frf` from a 12-element FE cantilever rather than
against `femtools.mpe.synthetic` alone. 4 responses, 1 reference, 1 % modal
damping, 1601 lines to 200 Hz:

| estimator | FRF noise | max frequency error vs the FE truth |
|---|---|---|
| `poly_lscf` | 0 % | **0.0000 %** (damping error 0.000 %) |
| `lsce` | 0 % | 0.0024 % |
| `poly_lscf` | 1 % complex | 0.0034 % |

Worth recording for whoever writes the round-2 MPE test: a rectangular-section
cantilever bends in two planes, and only two of the five FE modes below 200 Hz
are observable in a single-direction sensor set. My first version of this check
"failed" purely because it expected all five. Derive the expected list from the
modal participation `|phi_out| · |phi_in|` rather than from the frequency list,
or the test will chase a non-bug. LSCE also reports one extra pole at the top
band edge (199.995 Hz), which is a normal windowing artefact — match expected
modes to nearest identified, do not require an exact count.

## 6. Notes for other agents

- **CLI / IO (whoever owns `cli.py` and `femtools.io`).** `_load_model` returns
  a `Project` for `.ftproj`, but `_solve` and the other commands pass it
  straight to `solve_modes`, which duck-types on `.nodes` / `.elements`. I have
  worked around it inside `femtools.updating`, so `femtools update` works, but
  the other `.ftproj` commands are likely still broken. The real fix is one line
  in `_load_model`: return `getattr(project, "model", project)`.
- **Other examples are still failing**, all outside my scope, all with the same
  flavour of signature drift: `examples/frf_synthesis.py`
  (`as_damping` rejects a `model` key), `examples/mac_demo.py` (`pair_modes`
  has no `mac_min` argument), `examples/pretest_efi.py` (`EFIResult` has no
  `ed_final`). Worth a sweep by their owners — `for f in examples/*.py; do
  python3 "$f"; done` finds them in a second.
- **`docs/algorithms/optimization.md` §1 documents a model-first
  `size_optimize(model, design_vars, objective, ...)`.** The implementation is
  callable-first, `size_optimize(objective, x0, ...)`, which is what
  `docs/CONTRACT_API.md` pins (import path only) and what nothing else calls. I
  left it alone rather than churn a signature no caller uses, but if a
  model-driven FE sizing wrapper is wanted it can be layered on without
  touching the existing entry point.
- **Tests (R2-G1).** Two things the round-1 report already flagged still hold:
  EFDD damping carries 10–15 % scatter on a finite record, and a two-parameter
  beam updated from noisy frequencies alone is genuinely ill-conditioned. Add
  to that the MPE observability trap in §5.
