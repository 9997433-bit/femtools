## The bug: UNV roundtrip silently corrupted non-SI models

Reproduction (before the fix): build a cantilever in mm-N-tonne-s
(E = 210000 MPa, nodes at 500 mm), `write_unv` → `read_unv`:

- node coordinates were divided by the dataset-164 length factor
  (500 → 0.5) and the model tagged **SI**,
- but the dataset-30000 material/property tables came back **verbatim in
  mm units**: E = 210000 read as *pascals* (off by 10⁶), A/Iy/rho likewise.

The reloaded model was internally inconsistent — any downstream solve would
be wrong by orders of magnitude with **no warning**. This contradicts the
module's own "femtools round trips lossless" contract. (All existing tests
use SI models, which is why it stayed invisible.)

### Fix (backwards compatible, dataset 30000 format still version 1)

- `_write_cards_30000` now includes `"units": model.units.to_dict()` in the
  JSON payload — an **additive key**; pre-fix readers only call
  `payload.get("materials"/"properties")` and ignore it, so old femtools
  and all third-party readers see no difference.
- `read_unv` restores that unit system verbatim and skips the dataset-164
  coordinate rescale for femtools-authored files: every value in such a
  file (coordinates *and* cards) is stored in the model's own units, so the
  roundtrip is now exact and the model stays consistent
  (`units.check_consistent()` passes, zero warnings).
- Legacy behaviour is fully preserved elsewhere, verified explicitly:
  - foreign file (no dataset 30000): coordinates converted to SI per the
    UFF `value_si = value_file / factor` convention, note emitted — as
    before;
  - pre-fix femtools file (30000 without `units` key): legacy conversion,
    cards restored — byte-for-byte the old behaviour;
  - corrupt `units` entry: warning, cards still restored, legacy
    conversion (never an error).
- Module docstring updated (units paragraph + material/property gap
  section).

## Not fixed (checked, judged not bugs — documented for the orchestrator)

- **BEAM2 orientation is not carried through UNV** (written orientation
  record is node-id 0): dataset 2412 encodes orientation as a *node id*,
  femtools stores a *vector*, and inventing nodes would pollute the mesh.
  ftproj carries it losslessly; BDF writes it as CBAR X1,X2,X3. Format
  limitation, unchanged.
- **Complex-mode eigenvalue convention** (dataset 55 analysis type 3):
  reader and writer both use the pole λ (freq = |λ|/2π, ζ = −Re λ/|λ|),
  which is self-consistent and stable across read→write→read; nothing
  in-repo produces complex `ModalResult`s with ω² eigenvalues. Left alone;
  worth a docstring note in `ModalResult` if complex FEA modes ever land.
- **TRUSS2D → BAR2 across UNV** (rod descriptor 11), lumped auto-pid
  renumbering across BDF: documented Round-1/2 behaviour, not regressions.
